# 07 — Legal Acceptance

## 1. Purpose

Record authoritative evidence that an authenticated user accepted the required Terms of Service version and acknowledged the required Privacy Policy version before entering Habit Compass.

The existing Terms and Privacy screens remain the source documents. Codex must not rewrite their content as part of this feature unless separately instructed.

## 2. Data model

### Current legal versions

Recommended server-controlled table:

```sql
create type public.legal_document_type as enum (
  'terms',
  'privacy'
);

create table public.legal_document_versions (
  document_type public.legal_document_type not null,
  version text not null,
  effective_at timestamptz not null,
  is_current boolean not null default false,
  primary key (document_type, version)
);
```

Enforce only one current version per document type with an appropriate partial unique index or controlled update function.

### Acceptance records

```sql
create table public.legal_acceptances (
  id uuid primary key default gen_random_uuid(),

  user_id uuid not null
    references auth.users(id)
    on delete cascade,

  terms_version text not null,
  privacy_policy_version text not null,

  accepted_at timestamptz not null default now(),
  locale text not null,

  unique (
    user_id,
    terms_version,
    privacy_policy_version
  )
);
```

Optional future fields such as document checksum or region may be added later. Do not collect unnecessary personal data.

## 3. Authoritative timestamp

`accepted_at` is generated by Postgres/server time.

The client must not supply or override the authoritative timestamp.

Local pending state may remember that the user checked the box before an email/OAuth redirect, but that state is not legal evidence.

## 4. Controlled acceptance function

Use a security-definer database function or authenticated Edge Function, conceptually:

```sql
accept_current_legal_documents(p_locale text)
```

It must:

1. Resolve `auth.uid()`.
2. Reject unauthenticated calls.
3. Read the server-controlled current Terms version.
4. Read the server-controlled current Privacy version.
5. Validate/normalize supported locale.
6. Insert an acceptance row with server `now()`.
7. Use `on conflict do nothing` for idempotency.
8. Return the accepted versions and timestamp.
9. Use a fixed `search_path`.

The client must not be able to submit arbitrary version values as the authoritative current versions.

## 5. RLS

Enable RLS.

User policy:

- Select own acceptance records.

Do not provide general client policies for:

- Insert.
- Update.
- Delete.

Insertion occurs only through the controlled function. Acceptance records are append-only until complete account deletion cascades them.

## 6. Legal-status query

Provide one query/RPC that returns:

```ts
type LegalStatus = {
  accepted: boolean;
  currentTermsVersion: string;
  currentPrivacyPolicyVersion: string;
  acceptedAt: string | null;
};
```

A user is current only when an acceptance row exists for the exact current Terms and Privacy version pair.

## 7. First registration behavior

### Email/password

1. User checks legal acknowledgement before submitting sign-up.
2. App stores a short-lived pending intent with the displayed locale and current version identifiers.
3. User verifies email.
4. First authenticated callback checks server legal status.
5. If acceptance is missing and the pending intent is present, valid, and still matches the server's current versions, the app calls the controlled acceptance function.
6. The server records the authenticated user, server timestamp, current versions, and locale.
7. The pending intent is cleared.
8. If the intent is unavailable or invalid, show the legal-acceptance screen.
9. App enters Today only after an authoritative row exists.

### Google account creation

1. User checks legal acknowledgement on the sign-up screen before starting Google OAuth.
2. App stores the same short-lived pending intent.
3. OAuth callback authenticates the user.
4. If acceptance is missing and the intent remains valid, record acceptance through the controlled server function and clear the intent.
5. Otherwise show the legal-acceptance screen.
6. App enters Today only after acceptance exists.

### Returning sign-in

Returning users do not need a pre-auth legal checkbox on the sign-in screen. After authentication:

- Current acceptance: continue normally.
- Missing or outdated acceptance: show the legal-acceptance screen.

The pending intent is only a bridge across the redirect. The authoritative evidence is the server-created row associated with the authenticated user.

## 8. Legal acceptance screen

Show:

- Brief statement.
- Link to Terms of Service.
- Link to Privacy Policy.
- Required acknowledgement control.
- Primary `Agree and continue`.
- Sign-out action.

Do not show the main app shell.

If the user declines, the only available action is sign out. Account deletion for an account that was created but never accepted may be handled later by retention/cleanup policy; do not grant app access.

## 9. Future legal-version changes

When a version becomes current:

- Existing users without the exact current pair are routed to legal acceptance.
- Old acceptance rows remain unchanged.
- New acceptance creates another row.
- Do not overwrite history.
- The main application remains blocked until acceptance or sign-out.

## 10. Locale

Store the locale in which the acceptance UI/documents were presented, initially `en` or `es`.

Locale is contextual evidence, not an account preference replacement.

If the document links fall back to another locale, store the actual locale displayed.

## 11. Account deletion

Legal acceptance rows are user-owned account data for Habit Compass and must be deleted during permanent account deletion through the foreign-key cascade.

Any minimal deletion-operation log retained for reliability must not duplicate full legal acceptance history after deletion unless a separately reviewed legal obligation requires it.
